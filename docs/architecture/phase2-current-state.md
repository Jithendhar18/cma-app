# Phase 2 — Current State of the Data Architecture

Status: design input. Everything here was read from the code at commit `b2b32dc`. Nothing was changed.

## 1. Summary

The app is a single-user, local-only client. All data lives in three persisted Zustand stores. There is no concept of a user, course, syllabus version or exam attempt in the data model: the curriculum is a hand-written TypeScript table, and "Group I / Group II" are string labels.

The three findings that shape the whole Supabase design:

1. **Curriculum and personal progress are mixed in one record.** `Chapter` holds the official-looking fields (`title`, `order`, `estimatedHours`) *and* personal fields (`status`, `confidence`, `notes`, `actualHours`, …). In a multi-student database these must be split.
2. **Curriculum identity is positional.** Chapter ids are `subjectId + "-" + index` (for example `p5-3`), generated from the order of rows in `src/data/subjects.ts`. Inserting or reordering a chapter would silently change which chapter every saved record points to.
3. **The sample curriculum is not the official one.** `subjects.ts` states that its chapter outlines are demo content. Existing Phase 1 progress is attached to those sample chapters and cannot be mapped to verified official chapters automatically.

## 2. Persistence

| Store | localStorage key | Version | Contents |
| --- | --- | --- | --- |
| `studyStore` | `cma-study-os` | 3 | settings, chapters, sessions, revisions, focusLog, mockExams, practiceLog, meta |
| `timerStore` | `cma-study-os-timer` | 1 | the in-flight timer block and the current subject/chapter selection |
| `uiStore` | `cma-study-os-ui` | n/a | `sidebarCollapsed` only |

How persistence behaves today:

- Zustand `persist` rewrites the **whole snapshot** on every state change.
- On load, `loadSnapshot()` upgrades older data (`legacyMigration`), validates it (`snapshot.ts`), then rolls untouched demo dates forward (`demoRoll`). Unreadable data is copied to a `cma-study-os-corrupt-backup:*` key.
- Cross-tab sync uses the browser `storage` event, which calls `persist.rehydrate()` (`crossTab.ts`).
- Export is a JSON envelope (`exportVersion: 3`): the study snapshot plus the timer *selection* and sidebar state. A running timer block is deliberately never exported.
- A `demo` flag on seed records and `meta.seedAnchor` exist only so sample data can stay current. **Demo data must never be uploaded** to a server.

## 3. Entities and relationships as implemented

```text
Subject (static, code)          Settings (1 per browser)
   │ 1..n                           │ examGroups, examDate, examAttempt (free text)
Chapter ─────────────── progress fields live on the same record
   │ 1..n
   ├── StudySession   (a planned block: date, startTime, durationMinutes, status)
   ├── FocusRecord    (actually focused minutes, one per calendar day)
   ├── PracticeRecord (questions, correct)
   ├── RevisionTask   (1 | 2 | 3 | 'final', due, completed, cancelled)
Subject 1..n MockExam
```

Relationships are plain string ids with no enforcement. Records carry a redundant `subjectId` next to `chapterId`.

### Entity details

| Entity | Id format | Date and time representation | Notes |
| --- | --- | --- | --- |
| Subject | `p5` … `p12` (hard-coded) | none | `group` is the literal `'Group I' \| 'Group II'`; paper number is data |
| Chapter | `p5-3` (positional, hard-coded) | `lastStudied`, `completedOn` as `YYYY-MM-DD` | mixes curriculum and progress |
| StudySession (planned) | `s-<uuid>`; seed `s-1`…`s-8` | `date` `YYYY-MM-DD` + `startTime` `HH:MM` + minutes | stored status includes `missed`, but `missed` is also *derived* (`effectiveSessionStatus`) |
| FocusRecord | timer: `focus-<sessionKey>` and `focus-<sessionKey>@<date>`; planner: `plan-<sessionId>` and `plan-<sessionId>@<date>`; seed `f-<d>-<n>` | `date` only. No timestamp. | the id is the idempotency key |
| PracticeRecord | `pr-<uuid>`; seed `pr-<chapterId>-<n>` | `date` | |
| MockExam | `m-<uuid>`; seed `m-1`…`m-7` | `date` | per subject, `score` / `maxScore` |
| RevisionTask | `rev-<uuid>`; seed `rev-1`…`rev-15` | `dueDate`, `completedOn`, `cancelledOn` | `final` revision is a string |
| Settings | none | `examDate`, `finalRevisionDate`, times as `HH:MM` | mixes profile, enrollment and preferences |
| Timer state | `sessionKey` = start epoch ms as a string | epoch ms, plus `focusMsByDate` | device-local by nature |

Ids are generated by `newId(prefix)` = `` `${prefix}-${crypto.randomUUID()}` `` in `studyStore.ts`, and deterministically for focus and planner-credit records.

### Time model

- Every date is a **local calendar date string**; no time zone is stored anywhere.
- Day assignment for focus time is done at write time by `splitIntervalByDay`, using the browser's local midnight. A block that crosses midnight becomes one record per day, with whole minutes allocated by largest remainder so the total is exact.
- Because only `date` is stored, the original start/end instants cannot be reconstructed from existing records.

## 4. Stored versus derived

| Value | Today | Source of truth |
| --- | --- | --- |
| Daily and total study time (`StudyLog`) | derived (`buildStudyLog`) | `focusLog` |
| Chapter `actualHours` | **stored and also maintained by every action** | should be derived from `focusLog` |
| Chapter `questionsPracticed`, `correctAnswers` | **stored** and maintained | should be derived from `practiceLog` |
| Chapter `lastStudied` | **stored** and maintained | should be derived (latest record date) |
| Chapter `completedOn` | stored | genuinely stored: it is an event, not derivable |
| Chapter `status`, `confidence`, `notes` | stored | user input |
| Session `missed` | stored in enum, derived in UI | derived from date and status |
| Revision bucket (due / overdue / upcoming) | derived (`revisionBucket`) | `dueDate`, `completedOn`, `cancelledOn` |
| Subject completion, accuracy, weak areas, consistency, XP, level, badges, streaks | derived | records and chapters |

`validateConsistency` (Phase 1) exists precisely because the first three rows are denormalised duplicates. In Postgres they should become views, not columns (see `database-schema.md`).

## 6. Business rules already implemented (must survive the move)

These are enforced in application code and covered by tests. The database should enforce the structural ones and leave the scheduling logic in client code.

1. A chapter that reaches `completed`, `revision_due` or `exam_ready` gets at most one **pending** revision. Revision 1 is due the next day; completing it schedules revision 2 (+7 days), then 3 (+21 days), then `final` on the configured final-revision date.
2. Marking a chapter incomplete **cancels** its pending revisions (`cancelledOn`) and keeps them. Completed revisions are never touched. Completing the chapter again continues after the highest completed revision (`nextRevisionNumber`).
3. A revision cannot be both completed and cancelled. Cancelled revisions are excluded from counts, due lists and search.
4. Completing a planned session credits its minutes once. Un-completing removes only the records the planner itself created (`plan-<id>` and `plan-<id>@<date>`), matched exactly so `plan-s-1` never matches `plan-s-10`.
5. Deleting a planned session keeps the logged time and detaches it (`sessionId = null`).
6. Focus records are **idempotent by id**: adding an existing id is a no-op. A timer block that ends in two tabs, or is recovered after a refresh, can never be logged twice.
7. Time that crosses midnight is split across calendar days and the total never changes.
8. Practice cannot record more correct answers than questions attempted.
9. `confidence` is 1–5.
10. Mock `score` is between 0 and `maxScore`.
11. Demo records are flagged and may move; anything the user edits loses the flag and never moves.

## 7. How the UI consumes the data

- **Curriculum coupling:** 20 non-test files import `@/data/subjects` (51 references to `SUBJECTS`). Examples: dashboard grids, planner form, timer selects, reports, search, achievements, library filters, `seed.ts`, `legacyMigration.ts`, `seedValidation.ts`.
- **Routing:** `/subjects/:subjectId` uses the hard-coded subject id (`p6`) in links, search results and deep links (`?tab=chapters&chapter=p6-3`).
- **Selectors:** `lib/analytics.ts`, `lib/selectors.ts`, `lib/achievements.ts` are pure functions over arrays of the types above. They are the main reason the migration can be low-risk: if the repository layer returns the same shapes, these and their tests do not change.
- **Settings consumers:** `ExamCountdownCard`, `ExamCountdownWidget`, the settings page and revision scheduling read `examDate`, `examDateIsSample`, `finalRevisionDate`, `examGroups`.

## 8. Compatibility and migration risks

| # | Risk | Why it matters | Mitigation direction |
| --- | --- | --- | --- |
| R1 | Positional chapter ids | Any real curriculum edit would re-point saved progress | Stable keys and uuid primary keys; never reuse a key |
| R2 | Phase 1 data is tied to *sample* chapters | Cannot be mapped to official chapters automatically | Explicit user-driven mapping step, or import only chapter-independent data; see `frontend-migration.md` |
| R3 | 20 files hard-code the curriculum | The curriculum must become a runtime dependency | A `CurriculumProvider` with two sources (bundled sample for local mode, database for account mode) |
| R4 | Chapter totals are denormalised | Server and client could disagree | Derive in views; remove from synced fields |
| R5 | Whole-snapshot persistence | A naive sync would re-upload everything on every edit | Entity-level diff and outbox |
| R6 | `missed` stored and derived | Ambiguous source of truth | Store only the user-controlled states; derive `missed` |
| R7 | `Settings` mixes three concerns | Profile, enrollment and preferences have different owners and lifecycles | Split into `profiles`, `student_enrollments`, `user_settings` |
| R8 | No timestamps on focus records | Cannot be re-bucketed if the time zone changes | Keep `local_date` authoritative; add an optional `started_at` for new data |
| R9 | Demo flags and `meta.seedAnchor` | Must never reach the server | Exclude `demo` records from any upload; keep `meta` local |
| R10 | Cross-tab sync is a local-storage trick | Two tabs plus a server can double-write | Idempotent keys plus a single flusher (Web Locks) |
| R11 | `exportVersion: 3` file format | Existing backups must stay importable | Keep the JSON snapshot as the portable backup format; add a versioned adapter |
| R12 | Timer state holds `chapterId` | Chapter ids change type (string slug → uuid) | Timer selection is revalidated against the loaded curriculum on startup |

## 9. What this means for the design

- Split `Chapter` into **curriculum chapter** (shared) and **chapter progress** (personal, per enrollment).
- Replace positional ids with **uuid primary keys plus immutable `stable_key`s**.
- Make the focus log the **only** stored source for time; make chapter hours, questions and last-studied **views**.
- Keep scheduling rules in the client's pure functions; let the database enforce structure (uniqueness, foreign keys, check constraints, ownership).
- Treat the timer as device-local; sync only completed focus records.
- Keep the local-only mode working exactly as today, with the bundled sample curriculum.
